# 溯源系统分步开发指南（数据库模拟链/IPFS版本）

> 适用项目：`parts-trace-backend` + `parts-trace-frontend`
> 
> 目标：先在现有系统内完成 DID / 事件 / VC / 链条展示的可用闭环，区块链与 IPFS 先以数据库字段模拟，后续再平滑迁移。

---

## 0. 开发总原则

1. **先闭环再增强**：优先保证“可用 + 可查 + 可演示”。
2. **模拟链/IPFS统一适配层**：先落库，不要在业务代码中硬编码第三方 SDK 调用。
3. **接口前后兼容**：尽量不破坏已有接口，新增接口优先走 `/api/parts/did/*`、`/api/trace/*`、`/api/vc/*`。
4. **状态机明确**：DID、事件、VC 都必须有清晰状态流转，避免脏数据。

### 业务约定：批次 / 单件 / 工作台

- 操作层按**批次**组织，可信数据按**单件**落库：DID 与单件一一对应；同批次同环节可批量同款 VC（批次信息一致、单件标识唯一）。
- 表关系：`parts_info`（批次物料主数据）↔ `parts_unit`（展开单件）。界面「一条主数据 + 多个单件」与下拉里「几条 parts_info」差异见 [溯源数据与表说明.md](./溯源数据与表说明.md)。
- 溯源工作台组合接口示例：`POST /api/trace/workbench/batch-action`，`GET /api/trace/workbench/batches`，`GET /api/trace/workbench/batch-overview`，`GET /api/trace/workbench/batch-units`（以后端 `TraceEventController` 为准）。

## 2. 模块1：零部件 DID 身份管理（先做）

## 2.1 数据库变更（建议）

### 表：`parts_did` 新增字段

- `did_status` tinyint（0未激活 1已激活 2已冻结 3已归档）
- `doc_hash` varchar(256)
- `doc_cid` varchar(256)（模拟 IPFS CID）
- `chain_tx_id` varchar(256)
- `block_height` bigint
- `bind_type` varchar(32)（QRCODE/RFID）
- `bind_code` varchar(256)
- `unbound_time` datetime
- `remark` varchar(512)

> 先执行 `ALTER TABLE`，后续再合并到 `init.sql`。

### 可选新表：`did_generate_task`（异步任务）

- `task_id` varchar(64) PK
- `parts_id` bigint
- `status` tinyint（0排队 1处理中 2成功 3失败）
- `progress` int
- `result_did` varchar(256)
- `error_msg` varchar(512)
- `create_time` datetime
- `update_time` datetime

---

## 2.2 DID 生成规则（按需求）

格式：

- `did:industrial:part:[network]:[unique-identifier]`

其中 `unique-identifier`：

- 由 `生产商DID + 批次号 + 零部件序列号 + 时间戳` 做 hash 生成

建议实现：

- 在 `DidUtil` 增加 `generatePartDid(network, manufacturerDid, batchNumber, partsCode, timestamp)`
- 先用 `SHA-256` + 截断（如前 32 位）

---

## 2.3 后端接口（建议）

基于 `PartsController` 新增 DID 相关接口（或单独 `PartsDidController`）：

1. 同步生成 DID
- `POST /api/parts/{partsId}/did/sync`

2. 异步生成 DID
- `POST /api/parts/{partsId}/did/async`

3. 异步任务进度
- `GET /api/parts/did/task/{taskId}`

4. DID 列表查询（支持模糊）
- `GET /api/parts/did/list?partsId=&batchNumber=&did=&status=`

5. DID 文档查看
- `GET /api/parts/did/{didId}/document`

6. DID 文档下载
- `GET /api/parts/did/{didId}/document/download`

7. 绑定物理标识
- `POST /api/parts/did/{didId}/bind`（bindType/bindCode）

8. 解绑
- `POST /api/parts/did/{didId}/unbind`

9. DID 有效性校验
- `GET /api/parts/did/validate?did=...`

10. 冻结 / 解冻
- `POST /api/parts/did/{didId}/freeze`
- `POST /api/parts/did/{didId}/unfreeze`

## 3. 模块2：溯源事件记录（第二步做）

## 3.1 数据模型建议

### 新增表：`trace_event_type`
- 标准事件类型管理（增删改启停）

### `trace_event` 扩展
- `parts_did` varchar(256)
- `batch_number` varchar(128)
- `upstream_event_id` bigint
- `attachment_cid` varchar(256)
- `event_hash` varchar(256)
- `retry_count` int
- `chain_status` tinyint（0待上链 1成功 2失败）
- `abnormal_mark` tinyint
- `abnormal_reason` varchar(512)
- `audit_status` tinyint

> 事件录入前必须检查 DID 状态 = 已激活。

## 3.2 关键业务规则

- 一个零部件 DID 可对应多个事件
- 一个事件只能对应一个 DID
- 附件 hash 必须进入 `event_hash` 计算
- 上链失败自动重试最多 3 次（先数据库模拟）

## 4. 模块3：VC 签发与管理（第三步做）

## 4.1 数据模型建议

### 新增表：`vc_template`
- 模板与事件类型一一对应

### 新增表：`vc_verify_record`
- 记录每次验证结果（成功/失败原因/耗时/来源）

### `verifiable_credential` 扩展
- `vc_status`（已签发/已过期/已撤销/已归档）
- `vc_hash`
- `vc_cid`
- `issuer_org`
- `holder_did`

## 4.2 签发策略

- 自动签发：事件上链成功触发
- 手动签发：用户从事件发起
- 权限校验：仅事件所属机构可签发

## 4.3 验证流程

1. 解析 DID/VC ID
2. 取链上摘要（先 DB）
3. 拉完整 VC（先 DB）
4. 签名校验
5. 哈希校验
6. 归属校验
7. 状态校验

---

## 5. 模块4：溯源链条聚合与展示（第四步做）

## 5.1 聚合接口

- `GET /api/trace/chain/{did}`
- 返回 DID 信息 + 事件时间轴 + VC 列表 + 校验结果

## 5.2 校验接口

- `GET /api/trace/chain/{did}/verify`
- 输出问题节点（缺事件/缺VC/哈希不一致/签名异常）

## 5.3 报告接口

- `GET /api/trace/report?did=...&format=pdf|excel`

> 第一版可先输出 JSON / CSV，PDF后置。
