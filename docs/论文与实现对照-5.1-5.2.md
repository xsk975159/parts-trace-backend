# 论文第 5 章 5.1 / 5.2 与本项目对照及落地路线

本文档对应学位论文中 **5.1 基于 DID 的零部件全生命周期可信溯源模型** 与 **5.2 支撑溯源数据分离存储的跨链协作机制**，说明：论文要求在做什么、仓库里已经有什么、建议的实现顺序、以及配置开关如何对接。

---

## 1. 目标与原则

- **5.1 优先闭环**：DID 生成与绑定 → 溯源事件 → VC 签发 →「链上锚定哈希 + 链下完整文书」→ 查询验真。业务代码通过 `ChainStorageAdapter` / `ObjectStorageAdapter` 与底层解耦，换真链、真 IPFS 时不应大面积改 Service。
- **5.2 分期实现**：跨链网关、SPV/默克尔证明、异构链属于独立子系统；在 5.1 锚点合约与单一长安链联调稳定前，不建议并行深耦合。
- **当前默认**：`parts.trace.storage.chain-mode=db`、`object-mode=db`（数据库模拟链与对象存储，保证无外部依赖即可演示）。

## 2. 5.1 DID / VC 可信溯源 —— 对照表

| 论文要点 | 本项目对应能力 | 现状 | 建议后续开发 |
|----------|----------------|------|----------------|
| 零部件 DID（W3C 形态、`did:` 方法） | `parts_did`、`DidUtil`、`PartsDid` | 已有字段与生成逻辑 | 对齐 method/network 命名；链上 DID Registry 合约（可选） |
| DID 文档（公钥、服务端点） | `doc_hash`、`doc_cid`、`PartsDid` | 多为应用层/库表 | 完整 JSON-LD 文档；文档哈希或 CID 上链 |
| DID → 凭证 ID 列表 → 完整 VC | `verifiable_credential` 表、`TraceEventService` 聚合 | 关系在库中可建 | 合约 `append_vc` 与库表并行；或 Merkle 根 |
| 链上存 VC 哈希、链下存全文 | `VerifiableCredentialServiceImpl` → 适配器 | 已实现 `storeAnchor` + `appendVcIfSupported` | `chainmaker` + `chainmaker.sdk.invoke-enabled=true` 时走真实交易；`object-mode=ipfs` 时写 Kubo |
| BindVC / VerifyVC 算法 | 验签与哈希校验在 Service 层 | 部分在业务中 | 与论文章节对齐的四步验：哈希、归属、签名、状态 |
| 状态机合约（环节准入） | 规则库 + 异常模块 | 应用层为主 | 可按 [链上异常检测扩展说明.md](./链上异常检测扩展说明.md) 增量上链 |

**关键代码入口（便于检索）**

- 事件锚定：`TraceEventServiceImpl` → `chainStorageAdapter.storeAnchor(ChainAnchorRequest…)`
- VC 锚定与 VC 列表上链：`VerifiableCredentialServiceImpl` → `storeAnchor` 后 `appendVcIfSupported`
- DID 文档锚定：`PartsServiceImpl.generateUnitDid` → `storeAnchor`（含 `objectCid`、`partsDid`）
- 模拟链：`DbChainStorageAdapter.storeAnchor`
- 长安链：`ChainMakerChainStorageAdapter` —— 若 `ChainMakerSdkInvoker` 已初始化则 `invokeSaveAnchor` / `invokeAppendVc`；否则打日志并 **DB 镜像**（`blockchain_record`），业务不中断
- SDK 封装：`ChainMakerSdkInvoker`（`chainmaker.sdk.invoke-enabled=true` 时加载）
- 跨链主链接收：`CrossChainRelayService` → `invokeReceiveCrossAnchor`（SDK 未就绪时仅 debug 日志）

**智能合约（5.1 最小集，已实现源码）**

- 见 [chainmaker/合约设计.md](./chainmaker/合约设计.md) 与 `contracts/trace_anchor/`：`save_anchor`、`append_vc`、`revoke_vc`、`receive_cross_anchor`。

## 4. 配置开关（已实现）

在 `application.yml` 中：

```yaml
parts:
  trace:
    storage:
      chain-mode: ${PARTS_TRACE_CHAIN_MODE:db}    # db | chainmaker
      object-mode: ${PARTS_TRACE_OBJECT_MODE:db}  # db | ipfs

chainmaker:
  config-path: classpath:chainmaker/sdk_config.yml
  wasm-contract-name: ${CHAINMAKER_WASM_CONTRACT:trace_anchor}
  sdk:
    invoke-enabled: ${CHAINMAKER_SDK_INVOKE_ENABLED:false}
    invoke-timeout-ms: ${CHAINMAKER_INVOKE_TIMEOUT_MS:60000}
```

- **db / db**：当前默认，零依赖，适合开发与论文原型验证。
- **chainmaker + invoke-enabled=false**：使用 `ChainMakerChainStorageAdapter`，SDK 不发起交易，仍写 `blockchain_record` 镜像。
- **chainmaker + invoke-enabled=true**：需有效 `sdk_config.yml` 与链上已部署的 Wasm 合约，业务锚定与 `append_vc` 走真实 `invoke`。
- **db 或 chainmaker / ipfs**：启用 `IpfsObjectStorageAdapter`，需 Kubo（`IPFS_HOST`、`IPFS_PORT`）。

长安链 SDK 节点配置：`src/main/resources/chainmaker/sdk_config.yml.example` → 复制为 `sdk_config.yml`（勿提交真实密钥）。

## 8. 跨链怎么实现（分阶说明，由易到难）

核心认识：**跨链 = 在链 B 上「可信地采纳」链 A 已发生的事实**。论文里的网关、SPV、多模块验证，都是在解决「链 B 如何不全量同步链 A 还能相信这条消息」。

### 阶段 A —— 原型最小闭环（推荐先做，写论文写清假设）

适合：两条链都已能发交易（可两条都是长安链 dev）。

1. **定一条「主链 / 监管链」**：只存摘要（partDID、业务类型、contentHash、**sourceChainId**、源链 **txHash**）。
2. **从链**：沿用现有 `storeAnchor`，业务照常锚定。
3. **中继服务（网关 MVP）**：独立小进程或后端定时任务：从链交易确认 → 组装消息 → 调用主链 **`receive_cross_anchor`**（见 `CrossChainRelayService`）。
4. **信任模型**：中继用 **授权密钥** 调主链合约（联盟预置节点）。

**与现有代码衔接**：在锚定成功后，除写 `blockchain_record` 外，可给 `cross_chain_outbox` 插待转发记录，由中继消费。

### 阶段 B —— 论文式「可验证证明」（加强版）

在阶段 A 的 message 上增加：源链 **区块头哈希**、**交易默克尔路径**（或收据）；主链侧验证合约或链下验证引擎。

### 阶段 C —— 异构链

网关内双 SDK、统一消息体、验证逻辑按链类型分支。**建议在 5.1 单链锚点稳定后再做**。

### 与分层存储（IPFS）的关系

跨链只传摘要与 CID，全文仍从 **同一套 IPFS** 拉取并本地 `hash` 比对。
