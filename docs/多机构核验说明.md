# 多机构跨链存证核验

本文路径和命令相对于`parts-trace-backend/`。该功能在原跨链网关中增加多机构独立核验和联合签名门槛，支持长安链与FISCO BCOS 3.x。默认关闭，未配置时继续使用原授权中继流程。

## 1. 当前实现范围

协调端并行向不同机构的验证服务请求核验。每个验证服务先验证协调端请求签名，再通过自己的SDK连接读取源链存证及源交易。核对摘要、DID、CID、交易编号、区块高度、目标合约和`save_anchor`调用参数后，才使用自己的RSA私钥签名。

四节点配置至少需要三个不同节点的有效签名。协调端核对签名后将确认凭据写入数据库，再提交主监管链；目标合约再次验证委员会版本、成员身份、签名门槛、消息时间和重复内容。开启委员会后，旧的单中继入口不能绕过门槛。

| 已实现 | 仍属于扩展设计 |
| --- | --- |
| 独立验证接口、请求认证、并行取票、门槛判断 | VWABC广播、提议批次边界向量及全局排序 |
| 确认凭据持久化、过期续签、上链失败重试 | TVBA/MVBA、两步同步与协议路径切换 |
| 两种链上的联合签名检查和前端状态 | 源链轻客户端、独立共识证明和Merkle包含证明 |

这属于多机构联合核验，不是完整AionBFT实现。`3f+1`节点和`2f+1`签名是本功能采用的配置门槛，不代表已经实现异步BFT的一致性和活性保证。来源核验仍信任各节点配置的RPC/SDK连接；若所有验证节点都依赖同一被控制的RPC，不能据此保证来源真实。签名不能证明检测记录如实反映实物质量。

## 2. 配置前提

准备四个分别管理的验证节点，例如制造商、质检、物流和监管机构。每个节点持有一把独立的RSA私钥，协调端只保存这些节点的公钥。组织ID、公钥、节点ID和协调端使用的端点不得重复；程序可以检查配置重复，实际机构是否独立仍由部署管理保证。

各验证端应具备三条源业务链的存证和交易查询权限，采用各自受信的节点连接和SDK身份。验证端不需要取得协调端私钥。私钥格式为PKCS8 DER的Base64，公钥格式为X.509 DER的Base64；RSA为2048至4096位、指数65537。

目标合约需包含`relay_policy`、`configure_relay_committee`及`receive_cross_anchor_quorum`。合约仍使用`parts-trace-anchor/v2`业务格式，通过单独查询委员会验证是否支持新功能。旧合约缺少该接口时，启用协调端会明确失败。

沿用原来的受信源链配置：长安链`relay_public_keys`和FISCO部署清单`relayPublicKeys`仍用于限定允许汇聚的源链；它们与委员会成员公钥分别管理。实际合约升级、旧地址和历史状态迁移应先在测试链验证，本功能不会自动操作现有链。

## 3. 数据库与应用配置

先备份协调端数据库，在已完成原有增量升级的库中执行：

```sql
SOURCE src/main/resources/db/V20261026__relay_confirmation.sql;
```

该脚本只创建`relay_confirmation`表，可重复执行。新建测试库使用`init.sql`时已包含此表。默认关闭该功能的已有库无需为此修改结构；启用时会检查表是否可用。

将[配置样例](../src/main/resources/confirmation/relay-confirmation.yml.example)复制到部署目录，填写四个成员的公钥和完整接口地址。远程接口使用HTTPS；本机测试允许`localhost`、`127.0.0.1`或`::1`的HTTP地址。接口固定为`/internal/relay/endorse`，客户端不跟随重定向。

| 配置 | 作用 |
| --- | --- |
| `RELAY_CONFIRMATION_ENABLED` | 协调端启用联合核验，默认false |
| `RELAY_VALIDATOR_ENABLED` | 提供验证节点接口，默认false |
| `RELAY_VALIDATOR_ONLY` | 仅作验证节点，停止存证和中继后台任务，默认false |
| `RELAY_COMMITTEE_VERSION` | 与主链委员会版本完全一致，首次为1 |
| `RELAY_COORDINATOR_PUBLIC_KEY` | 校验协调端请求；协调端还会核对它与`RELAY_PRIVATE_KEY`是否匹配 |
| `RELAY_VALIDATOR_ID` | 当前验证节点在成员列表中的ID |
| `RELAY_VALIDATOR_PRIVATE_KEY` | 当前验证节点自己的私钥 |
| `relay.confirmation.members` | 节点ID到机构ID、公钥和接口地址的映射 |
| `relay.confirmation.faulty-nodes` | 配置参数f，支持1至3，对应4、7或10个节点 |
| `relay.confirmation.timeout-ms` | 单次HTTP连接/读取超时，范围500至10000毫秒 |

四节点样例使用`RELAY_MANUFACTURER_PUBLIC_KEY`、`RELAY_QUALITY_PUBLIC_KEY`、`RELAY_LOGISTICS_PUBLIC_KEY`和`RELAY_REGULATOR_PUBLIC_KEY`；相应`*_ENDPOINT`指定实际地址。

协调端在原有真实链配置基础上设置`RELAY_CONFIRMATION_ENABLED=true`，另外两个开关保持false，保留原有`RELAY_PRIVATE_KEY`用于签署核验请求。

各验证端设置`RELAY_VALIDATOR_ENABLED=true`、`RELAY_VALIDATOR_ONLY=true`、`RELAY_CONFIRMATION_ENABLED=false`，填写自己的ID与私钥、协调端公钥和完整成员公钥名单。仅验证模式不要求`RELAY_PRIVATE_KEY`，也不会代替协调端执行后台任务。验证服务仍使用本项目后端，需要其数据库和SDK基本配置。

配置文件通过Spring外部配置加载，例如：

```powershell
java -jar target/parts-trace-backend-1.0-SNAPSHOT.jar --spring.config.additional-location=file:/deploy/confirmation.yml
```

`/deploy/confirmation.yml`为示例绝对路径；Windows可替换为实际盘符路径。各实例使用各自端口和SDK身份，远程接口由TLS反向代理转发。

## 4. 主链委员会配置

将[委员会清单](../src/main/resources/confirmation/committee.example.json)复制到部署目录，填入主链SDK配置、实际链ID和与应用完全一致的成员公钥。FISCO目标需将`platform`改为`FISCO_BCOS`，填写`contractAddress`、`group`、固定`expectedAccount`和TOML配置地址。使用合约所有者的SDK身份执行配置。

```powershell
java '-Dloader.main=com.kewei.parts.infrastructure.confirmation.RelayCommitteeConfigurator' -cp target/parts-trace-backend-1.0-SNAPSHOT.jar org.springframework.boot.loader.PropertiesLauncher /deploy/committee.json
```

默认只读取链与合约身份、当前委员会并检查拟配置名单，不发送交易。确认清单后，在命令末尾增加`--apply`，才发送配置交易。工具不会启动业务HTTP服务或连接数据库。相同版本和名单已配置时只核对并返回；新版本必须比链上版本严格增加1，不能用旧版本覆盖新版本，也没有降级为零门槛的操作。

长安链调用合约方法`configure_relay_committee`，参数`committee`为清单中的委员会JSON。FISCO调用同名方法，工具把成员公钥转换为模数和指数数组。首次部署FISCO时，也可以在原部署清单中提供`committeeVersion`和`committeeMembers`，由部署工具在成功部署后配置。

先完成合约和成员配置，再启用协调端。协调端启动和每次提交前都会读取主链`relay_policy`，核对版本、人数门槛、机构和公钥，避免只在应用层设置门槛而链上仍接受单签名。

## 5. 确认状态与失败处理

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 正在向验证节点请求核验 |
| `WAITING` | 本次有效签名不足，不提交主链 |
| `CONFIRMED` | 已取得并保存足够签名，等待主链成功回执 |
| `COMMITTED` | 已取得主链成功回执 |

状态保存在`relay_confirmation`，不改变原`cross_chain_record`的0、1、2、3、-1定义。追溯查询页面在功能启用时显示机构核验状态和签名人数，并继续显示真实同步状态与主链交易。

联合签名覆盖原十个跨链字段，并增加`committee_version`和固定的`proof_type=relay-quorum/v1`，沿用按字段名排序、逐行`名称=值\n`的UTF-8原文。协调端请求使用额外的`relay-endorsement-request/v1\n`签名域，不能把节点投票用作协调端授权。

目标合约只接受其时间之前300秒至之后60秒内的消息。重试时可复用仍有效的确认凭据；临近过期或委员会变更时重新取得签名。主链暂时不可用时保留已保存的确认凭据，不把“已核验”写成“已上链”。已有源交易的业务内容不可被新签名覆盖。

失败沿用原中继队列重试策略，最多自动尝试10次。管理员可调用`POST /api/admin/chain-tasks/relay/{id}/retry`重新加入队列；它不会清除或绕过核验要求。验证节点接口采用整个请求的RSA签名认证，不使用业务用户JWT，也不提供修改委员会的HTTP接口。

## 6. 验证方式

后端测试覆盖四个本地HTTP验证端、单节点不可用、身份冒充、错误签名、过期凭据、内容冲突、持久化后重用、仅验证模式、源交易参数检查，以及两种目标链的路由。合约使用同一份Java生成的公开签名向量验证互操作；测试向量不含私钥。

```powershell
mvn test
cd contracts/fisco
npm ci --ignore-scripts
npm test
```

长安链在`contracts/trace_anchor/`执行`go test ./...`。本节的联合签名测试使用模拟源链读取、本地HTTP验证端和本地EVM，验证结果限于该环境。平台另已完成长安链2.3.10与FISCO BCOS 3.16.3的单机实链联调，采用授权中继签名，未启用多机构联合核验服务，详见[测试说明](测试说明.md)。四家机构独立部署、联合核验的实网吞吐量和协议级拜占庭故障实验尚未验证。
